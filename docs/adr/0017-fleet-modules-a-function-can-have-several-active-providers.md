# ADR-017 — "Fleet" modules: a function can have several providers active at the same time

- **Status**: accepted
- **Discussion**: predates the issue-based process (ADR-049)

Context: `internal/resolver`/`internal/broker` so far assume that a function has exactly **one** active provider at a time (chosen explicitly or by default, repointable during a seed → target handover, doc 05). This model suits `dns.zone`, `time.ntp`, `pki.issuer`: a single CoreDNS or PowerDNS is active, never both. Milestone M8 replaces the classic OpenSSH bastion with **Teleport in full agent mode** (user decision): its presence in the spec must affect *every* VM in the fleet (each module that provisions a VM must deploy the Teleport agent on it), and several modules of this kind can coexist (Teleport and, later, a monitoring/logging agent) — unlike DNS/NTP/CA, this is not an exclusive choice between competing products but a set of modules all active at once. The project always builds an entire infrastructure from scratch, never an addition to a fleet already in production (explicitly confirmed by the user): the classic DAG planner therefore already resolves the build order (a "fleet" module such as Teleport is built before any module that depends on it, like any other required function) — no reactive/event-driven mechanism is needed for VMs "added later", which do not exist in this model.

Alternatives: (a) the "fleet" module discovers the already provisioned VMs itself (new `compute.vm/v1.ListVMs` function) and connects to them with its own SSH key, deployed as an additional authorised key on each VM — rejected: it complicates the secrets model (keys are currently strictly isolated by owner/consumers) for no benefit, since the problem it would solve (VMs added afterwards) does not arise here. (b) Extend `os.base/v1` with explicit knowledge of Teleport — rejected for the same reasons as ADR-016 (coupling a generic contract to a specific product).

Decision: a function can be declared "multi-provider" (as opposed to the default "single active provider" mode) — every installed module that provides it is called, **all** of them, with the same `target` the caller already uses for its own calls (`os.base`, `core.ansible`): there is never any need to share an SSH key between modules. For M8: a new `fleet.agent/v1` function (`Install(target)`), provided by `teleport`. Each module that provisions a VM (`chrony`, `powerdns`, `vault`, and any future module) declares `fleet.agent/v1` in its `requires` and calls it from `Configure`, just as it already calls `TrustCA`/`SetResolver`/`SetNTP` — the resolver guarantees that all providers of `fleet.agent/v1` are built before it (classic DAG). If no "fleet" module is installed, the call is a no-op (zero providers).

Consequence: `internal/resolver`/`internal/broker` gain a second resolution mode ("fan-out to N providers" in addition to "single active provider, repointable"). `chrony`/`powerdns`/`vault` (already written) are changed once to add this generic call — a one-off cost, not repeated for each future "fleet" module added later (monitoring, logging…).
