# 06 — Secrets and state

## Principle
The user provides only the hypervisor credentials (by reference). **Every other secret is generated, stored and distributed by the tool.**

## Interface

```go
type Ref string // e.g. "pki/root-ca-key" — the only type that leaves the store

type Store interface {
    Ensure(ctx context.Context, ref Ref, gen Generator, meta Meta) error // creates if missing
    Get(ctx context.Context, ref Ref) (Secret, error)                    // Secret redacts String()/MarshalJSON
    Put(ctx context.Context, ref Ref, s Secret, meta Meta) error
    List(ctx context.Context, prefix string) ([]Entry, error)           // metadata only
    Backend() string
}

type Meta struct {
    Owner      string    // owning capability
    Consumers  []string  // consuming capabilities / VMs
    Kind       string    // password | token | private-key | certificate | ssh-key
    CreatedAt  time.Time
    Rotation   string    // never | on-handover | 90d …
    Recovery   bool      // must remain as a local copy after handover
}
```

Provided generators: password (32 characters, safe alphabet), random 256-bit token, ECDSA P-384 / Ed25519 key, Ed25519 SSH key pair, certificate (through the `pki.issuer` function).

## Backends
### `file` (seed, iteration 1)
- `state_dir/secrets/` directory, one file per secret, **age**-encrypted with the master key; metadata in a separate file, not encrypted but holding no secret value.
- Permissions `0700` on the directory, `0600` on files, owned by the tool's user.
- Master key: `state_dir/master.key`, generated by `init`, **displayed once** with a backup warning.
- Atomic writes (temporary file + rename).

### `vault` (target)
- KV v2 engine, path `genesis/<env>/<ref>`, metadata as custom metadata.
- Tool authentication: a dedicated `genesis` AppRole, whose credentials are themselves in the `file` backend.

### `file` → `vault` migration
Triggered by the handover of the `secrets` capability: copy of each entry, verification by reading it back, switch of the active backend in the state. `Recovery: true` entries stay in `file`.

## Accepted debt (iteration 1)
Master key in plaintext on the seed's disk, Vault root token and unseal keys kept in the `file` backend. The `MasterKeyProvider` interface must exist from now on (with the `file` implementation only) so that TPM / Shamir / HSM can be plugged in later.

## Redaction
- `Secret` type: `String()` and `MarshalJSON()` return `***`.
- `slog` handler filtering attributes of type `Secret` and known patterns (Vault tokens, PEM keys).
- Automated test: a full end-to-end run capturing logs and state, searching for each generated secret value → it must be absent.

## State (`internal/state`)
- `state_dir/state.json` file, versioned (`schemaVersion`), atomic writes, file lock to forbid two concurrent `apply` runs.
- Contents: digest of the applied spec, VMs (name, ID assigned by the compute module, IP), status of each module and step, active provider of each function, module versions, endpoints, active secret backend, handover history.
- **Contains no secret value**, only `Ref`s.
- `genesis state export` produces an archive (state + encrypted secrets) for backup or for resuming from another seed.
- Later: state backend in Vault or GitLab after handover.
