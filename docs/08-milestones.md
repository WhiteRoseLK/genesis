# 08 — Milestones and acceptance criteria

> This document defines each milestone and its acceptance criteria. They are **tracked** on GitHub (ADR-049): one [GitHub milestone](https://github.com/WhiteRoseLK/genesis/milestones) per milestone, a parent issue labelled `milestone` and one sub-issue per PR.

Implement them in order. Each milestone can be delivered and tested on its own.

## M0 — Skeleton
- Monorepo: `cmd/genesis`, `internal/`, `sdk/` (its own go.mod), `modules/`; Apache 2.0 `LICENSE`, `NOTICE`, SPDX headers; `Makefile` (`build`, `test`, `lint`, `proto`); `buf` for protobuf.
- CI: lint, tests, dependency license check, **import rules** (core ↛ modules, modules ↛ core).
- **Accepted when**: `genesis --help` lists the commands of doc 02; a forbidden import makes CI fail.

## M1 — Spec and overall validation
- Types, defaults, structural validation, JSON Schema, rejection of literal secrets.
- **Accepted when**: the example of doc 04 is valid; 10 invalid specs fail with a YAML path.

## M2 — Secrets and state
- `init`, master key, age `file` backend, redaction, state with a lock.
- **Accepted when**: `Ensure` is idempotent; two concurrent `apply` runs → the second one refuses; the redaction test is green.

## M3 — SDK and module host
- `module/v1` protocol, `sdk.Serve`, `go-plugin` host, discovery, `genesis.lock` with digests, `genesis modules list/install/verify`, `genesis modules scaffold`.
- Test harness and conformance suite (skeleton).
- **Accepted when**: a module generated by `scaffold` compiles, is discovered and answers `Describe`; a module whose digest differs from the lock is refused; a module that crashes during a step produces a clean error without stopping the core.

## M4 — Resolver, broker, planner, engine
- Capability → module resolution (defaults, automatic additions, conflicts), broker with access control, `core.*` functions, DAG, `plan`, engine with resumption and audit.
- Test modules `test-a → test-b → test-c` with a seed phase and a handover, and the `fake-compute` module.
- **Accepted when**: correct order; cycle detected; a call to an undeclared function is refused by the broker; kill then re-run → resumption; second `apply` → 0 changes; **adding a `test-d` module that depends on `test-a`, without changing any file outside `test/modules/test-d/`** → inserted at the right place in the plan.

## M5 — `proxmox` and `base-os` modules
- **Accepted when**: `compute` spec + one placed VM → VM created, reachable, hardened; re-run → 0 changes; `destroy` deletes it; SDK conformance green.

## M6 — `chrony`, `coredns`, `powerdns` modules
- **Accepted when**: the `Verify` of doc 07 passes; after the handover, stopping `coredns` has no impact.

## M7 — `step-ca`, `vault` modules
- **Accepted when**: the `Verify` of doc 07 passes; non-`recovery` secrets migrated to Vault.

## M8 — `teleport` module and seed retirement
- **Accepted when**: connection through the Teleport agent works; after the automatic seed retirement at the end of `apply` (ADR-020), the environment is green.
- **Deferred repoint (debt, doc 07)**: refusing direct SSH access is not required at this milestone — `fleet.agent/v1.Install` leaves the native sshd active, and `core.ansible/v1` keeps using direct key-based access. Switching the core to the Teleport agent is tracked by a dedicated issue, outside the M8 scope.

## M9 — Hardening and proof of extensibility
- Full end-to-end test on Proxmox (`integration` build tag), user documentation and module guide (doc 10).
- Proof: a minimal `bind` module replacing `powerdns`, e2e green without changing the core or the other modules.
- **Accepted when**: the overall success criterion of doc 01 (< 30 min, idempotent) is met with `powerdns` **and** with `bind`.

## Iteration 2 (out of scope)
Air-gap (artefact and module bundle), GitLab, monitoring, backup, Nutanix module, Vault HA, day 2, module signing and registry, hardware root of trust, then the physical layer (`pxe-seed`, `redfish`, `proxmox-install`).
